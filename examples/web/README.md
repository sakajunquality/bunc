# Bun web app on bunc

This example is a Bun HTTP server packaged as an OCI image by bunko. The same
image runs with bunc's JavaScript entrypoint or its standalone Linux executable.

From the repository root:

```sh
bun install --frozen-lockfile --ignore-scripts

# JavaScript runtime, in a disposable Docker host:
bun run demo:docker

# Standalone runtime, with no separately installed Bun in that Linux host:
bun run demo:docker:standalone

# Apple Container alternatives (Apple silicon Mac):
container system start
bun run demo:apple
bun run demo:apple:standalone
```

Choose one command, open the printed URL, then press Ctrl-C to stop it. Docker
uses `http://127.0.0.1:18080/` by default; Apple uses the assigned VM IP on port
8080. For a second Docker demo, pass a different port:

```sh
bun scripts/lab.ts docker --standalone --port 18082
```

The first run builds `.bunc-output/image` using the pinned bunko dev dependency.
Later runs reuse it. All files generated by these commands are ignored by Git.
To build an edited example, use a fresh directory (choose `linux/amd64` on x64):

```sh
bunx --no-install @sakajunquality/bunko build examples/web \
  --base oven/bun:1.4.2-distroless --platform linux/arm64 \
  --push=false --git-metadata=false --oci-layout .bunc-output/web-next
bun scripts/lab.ts docker --standalone --layout .bunc-output/web-next
```

## What the response checks

`GET /` returns JSON reporting the image's environment message, Bun version,
PID, UID/GID, working directory, hostname, root visibility, writable temporary
storage, read-only root mount, and selected `/proc/self/status` fields.
`GET /missing` returns 404. The SIGTERM handler logs receipt and exits normally.

```sh
bun run test:docker
bun run test:docker:standalone
bun run test:apple
bun run test:apple:standalone
```

Verification starts the app, checks the JSON and 404 response, sends SIGTERM,
checks graceful exit and temporary-rootfs cleanup, and removes the disposable
host. Results go to `.bunc-output/results/`; standalone results have a
`-standalone` suffix. This verification expects this example's exact response,
not an arbitrary web application's response.

## Which Bun is running?

- The **build/demo tools** run with Bun installed on your development machine.
- **bunc in standalone mode** includes its own Bun runtime in the executable.
  The demo deletes the outer Linux host's installed `bun`/`bunx` before starting
  bunc. The worker re-executes that same bunc binary inside fresh namespaces.
- The **application** runs the Bun executable already present in the bunko-built
  OCI image after bunc switches to its root filesystem. The HTTP `bun` field
  reports this application's Bun version, not the host runtime's version.

The compiled bunc still needs Linux, glibc, and util-linux `unshare`. This remains
a trusted-image experiment in a privileged disposable Linux environment; see
the repository's [security scope](../../SECURITY.md).
